# 向量库选型笔记

> 整理日期：2026-08-18
> 背景：面向教培场景的 AI 学习产品，为老师/学生的资料做检索。硬约束：**本地部署、数据不出环境**，不接受把用户资料交给第三方。

## 一、主流向量库横向对比（规模定位）

| 方案 | 类型 | 适合规模 | 核心特点 |
|---|---|---|---|
| **pgvector** | Postgres 扩展（开源） | 单节点 ~1000万~5000万 | 向量与业务数据同库，SQL 过滤、事务一致，已有 Postgres 时零新增组件 |
| **pgvectorscale** | Timescale 扩展 | 1000万~5000万 | 官方基准：5000万向量、99% recall 下 471 QPS，p95 比 Pinecone s1 低 28 倍（供应商自测） |
| **Qdrant** | 独立向量库，Rust 开源 | 单机到亿级，分布式模式十亿级 | payload 过滤强（按机构/班级/学科过滤）；多份社区基准中延迟最低 |
| **Pinecone** | 全托管云服务（闭源） | 托管平台亿~十亿级 | 零运维、自动扩缩容；基准中 recall 略低（~95%）、延迟偏高（p95 ~48ms） |
| **Milvus** | 独立向量库，开源 | 十亿级，企业级 | 读写节点分离，写入/查询隔离最好；运维复杂度最高 |
| **Weaviate** | 独立向量库，开源 | 千万~亿级 | 内置混合检索（关键词+向量一次查询），开箱即用体验好 |
| **ChromaDB** | 轻量/嵌入式 | 100万以下 | 原型验证、本地开发最快 |
| **LanceDB** | 嵌入式 | 本地优先 | 适合个人工具/桌面场景 |

### 性能关键数据（概览，来源见文末）

- 召回率（准确优先配置）：Qdrant ~99.2% > Milvus ~99.0% > pgvector ~98.5% > Weaviate ~97.8% > Pinecone ~95%
- 延迟 p50：Qdrant ~3ms > Milvus ~4ms > pgvector ~5ms > Weaviate ~8ms > Pinecone ~12ms
- **注意**：各机构基准互相矛盾（pgvectorscale 官方自称远超 Qdrant，Qdrant 社区基准又称最快），均带自家立场；选型后须用自己数据压测。

## 二、按「本地部署」约束收敛

### 直接排除

| 方案 | 排除原因 |
|---|---|
| **Pinecone** | 纯托管云服务；Pinecone Local 仅是内存模拟器，官方明示仅供原型/CI，不可生产 |
| **Zilliz Cloud / Qdrant Cloud / Weaviate Cloud 等托管版** | 不满足约束；但其开源内核可自托管，取开源版即可 |
| **Astra DB / Supabase 托管等** | 同理，只取开源内核 |

### 本地部署短名单

| 方案 | 部署形态 | 适合规模 | 评点 |
|---|---|---|---|
| **pgvector** | Postgres 扩展，单机/自建 | <5000万 | 已有 Postgres 则零新增组件；向量与教务元数据同库过滤、权限好做 |
| **Qdrant** | 单个 Docker 镜像 | 单机到亿级，可扩集群 | 独立向量库中运维最省：单二进制、Rust 底层、payload 过滤强，完全离线可用 |
| **Weaviate** | Docker/K8s | 千万~亿级 | 混合检索内置；但内嵌向量化默认指向 OpenAI 等云端，本地化须显式关闭并配本地模型 |
| **Milvus** | Docker Compose / K8s | 十亿级 | 功能最强但组件多、运维重，未到该规模不建议 |
| **Chroma** | 嵌入式/单进程 | <100万 | 原型最快，数据文件在本地；多进程并发与持久化弱，不适合生产 |
| **LanceDB** | 嵌入式 | 本地优先 | 服务端多进程并发有限制 |

## 三、方案建议（决策路径）

1. **先看后端有没有 Postgres**：有 → 直接 pgvector，教务元数据过滤 + 向量检索同库完成，不多养组件。
2. **没有 Postgres、想独立演进** → Qdrant 单节点 Docker。初期配置极简，未来千万级向量仍在单机能力内，不必中途迁移。
3. **原型验证** → Chroma 或 pgvector 皆可；检索效果验证不依赖具体引擎，先跑通再定生产选型。
4. **Milvus 现阶段不碰**：读写分离、十亿级是其优势，现在引入等于提前背 K8s 运维负担。
5. **规模估算参考**：教培单机构 chunk 后通常几十万条向量；聚合多机构按 1000万~5000万 规划大概率够用，不需要一上来就分布式。

## 四、分块策略实验（自有数据）

> 2026-08 在自有教培资料上跑的分块参数实验，结论为定性评估，定量指标待补（见第六节待办）。

### 实验目的

在向量库选型收敛后，验证分块参数（chunk_size / overlap）对检索召回的影响，为文档入库策略定基线。

### 实验参数设计

| 组 | chunk_size | overlap | 说明 |
|---|---|---|---|
| A | 512 字 | 无 | 基线组 |
| B | 512 字 | 80 字 | 同块长 + 重叠 |
| C | 1024 字 | 150 字 | 大块 + 重叠 |

### 结果汇总

| 组 | 结论 |
|---|---|
| A（512 无重叠） | 召回偏低 |
| B（512 + 80 重叠） | 召回明显变好 |
| C（1024 + 150 重叠） | 长文档上效果最好；短问答会带入噪声 |

### 结论与建议

1. 默认优先 **512 字 + 80 字重叠**：召回与噪声平衡较好。
2. 长文档场景可切 **1024 字 + 150 字**，注意短问答场景的噪声问题。
3. 同文档混合切块（按内容类型选择块长）可作为后续方向验证。

## 五、隐私约束下的三个关键点（比选库更重要）

1. **Embedding 环节**：嵌入模型若走 OpenAI/Cohere 等云端 API，**文档文本会发给第三方**，选哪个向量库都白搭。必须用本地嵌入模型（BGE、GTE 系列，或 Ollama 部署）——这是「数据不出本地」的真正关键。
2. **遥测上报**：Qdrant、Chroma 等默认带匿名遥测，自托管时在配置文件显式关闭，再断外网验证一次。
3. **模型与依赖拉取**：完全离线环境需提前备好 Docker 镜像、模型权重、pip 包；若只是服务器不连外网但可内网拉包，此条可放宽。

# 对话式知识管家（Chat Knowledge Base）设计文档

- 日期：2026-07-09
- 状态：设计已确认，待编写实现计划

## 1. 背景与痛点

用户认可"写 wiki 记录内容"很有必要，但存在两个长期痛点：

1. **内容重复**：写了 A 文档，一段时间后同样的内容又写进了 B 文档，缺乏"单一事实来源"。
2. **结构难维护**：文档的目录结构会随时间和内容需要不断调整，人工维护成本高、容易越用越乱。

## 2. 产品愿景

一个**对话式知识管家**：

- 用户有什么要记住的内容，直接"说"给它，它自己决定如何组织并保存。
- 用户提问时，它能找到对应内容并回答（带来源）。
- 它同时能存取文件，需要时以附件形式返回。
- 用户把"组织文档结构"这件事完全交给它，不再操心"该放哪、是否重复"。

## 3. 核心设计原则

- **数据主权第一**：落地数据必须是用户**可读、可编辑、可迁移、完全可控**的。即使以后不用 AI，用户也能自行维护，或迁移到其它工具。
  - 定义澄清：数据信任 = "落地数据人类可读可控"，**不是**对 AI 保密。
- **隐私对 AI 默认可接受**：在此前提下，最大化利用 AI 提升产品能力与体验。
- **md 是唯一事实来源**：`目录 + md 文件` 是权威数据；索引（向量/全文）只是可重建的加速缓存，删除后能从 md 重建。
- **透明与可回溯**：AI 的每一次整理都有记录，可查看、可回滚。

## 4. 整体架构

**统一的"知识大脑"后端 + 多入口前端 + 用户可直接浏览的文件数据层。**

```
┌── 入口层（可陆续增加）──────────────┐
│  Web 聊天界面(MVP) │ 桌面Spotlight │ 微信/飞书 │
└───────────────┬────────────────────┘
                │  统一的对话/文件 API
┌───────────────▼────────────────────┐
│            知识大脑（后端核心）        │
│  ┌─────────┐  ┌──────────┐  ┌──────┐ │
│  │ 组织引擎 │  │ 检索引擎  │  │ 模型  │ │
│  │(写入/整理)│  │(混合检索) │  │ 抽象层│ │
│  └─────────┘  └──────────┘  └──────┘ │
└───────────────┬────────────────────┘
                │  读写
┌───────────────▼────────────────────┐
│   数据层（服务器上，用户可直接浏览）    │
│   目录 + md 文件  +  附件  +  git历史  │
│   +  向量/全文索引（可随时重建）        │
└─────────────────────────────────────┘
```

关键原则：**md 文件是唯一"事实来源"，索引只是加速缓存，删了能从 md 重建。**

## 5. 数据与存储布局

```
knowledge/                    ← 用户可直接浏览/编辑的知识库（git 仓库）
├── 技术/
│   ├── docker/
│   │   ├── 常用命令.md
│   │   └── attachments/
│   │       └── 部署方案.pdf
│   └── ...
├── 生活/
│   └── ...
└── .kb/                      ← 系统元数据（在 git 里，用户可无视）
    ├── changelog.md          ← AI 每次整理记录：动了什么、为什么
    └── index/                ← 向量 + 全文索引（可重建的缓存）
```

- **md 文件**：正文，人类可读。文件顶部有少量元信息（来源、时间、标签），不影响阅读。
- **附件**：word/ppt/xls/pdf/zip/rar 等原样保存在就近的 `attachments/`，需要时原样返回。
  - 可读类文件（word/ppt/xls/pdf）会被**抽取文本**进索引（使"问"能命中附件内容），但**原件永不改动**。
  - 二进制类文件（zip/rar 等）仅保存与登记，不抽取内容。
- **git**：每次写入/整理 = 一次 commit，天然提供历史、diff、回滚，支撑"完整变更记录"。
- **目录结构由 AI 维护**，但就是普通文件夹，用户随时可手动改，AI 尊重用户的改动。

## 6. 组织引擎

### 6.1 写入流水线（用户说一句话 / 传一个文件时）

```
1. 理解      小模型：这条内容讲什么？→ 提取主题/实体/标签/摘要
2. 找关联    混合检索：库里有没有相关/重叠的已有文档？
3. 决策      小模型：放哪个目录？新建文件 / 合并进老文件 / 追加？
             └─ 重叠但拿不准 → 暂存并【问用户】
4. 执行      写 md → git commit → 记入 changelog
5. 审核      大模型：抽检第 3 步决策是否合理，发现问题回滚/纠正
```

- 小模型负责"理解 + 决策"（快、便宜、可并行处理多条）；大模型只在关键节点"审核"。
- 全程透明：每步判断写入 changelog，用户能看到"为什么这么放"。

### 6.2 重叠处理策略（对应用户选择 C + D）

- **默认全自动处理**，并保留**完整变更记录**（可查看 / 可回滚）—— D。
- **仅当 AI 判断有重叠但拿不准时**，才暂存并征询用户 —— C。

### 6.3 目录结构随时间演化（针对痛点②）

采用 **"涌现 + 定期巡检整固"** 策略（方案三）：

- **日常写入**：即时、局部，按内容涌现式自动归置（不预设固定分类）。
- **后台"园丁" agent**：定期（或库达到一定规模时）做全局巡检——合并重复、拆分过杂文件、重组不合理分类。

**巡检的执行边界（可配置，默认如下）：**

- **小改动（自动执行）**：同目录内合并两个重复文件、重命名、单个文件挪位、补标签。
- **大改动（需用户审批）**：新建/删除顶层分类、批量移动多个文件、整体重构目录树。
  - 大改动以"可预览、可一键接受/拒绝的提议"形式呈现。

## 7. 检索与回答（混合方案 D）

```
1. 召回   向量语义 + 全文关键词 并行，拿到候选片段（含 md 正文和附件抽取文本）
2. 精排   小模型/重排，挑出最相关的几段
3. 整合   大模型：基于片段组织回答，并【标注来源文件】
4. 附件   若命中的是文件（pdf/word/zip…），把原文件作为附件一并返回
```

- 回答**必须带来源**（指向具体 md/文件），用户可点开核对，防止臆造。
- 找不到时**如实告知没有**，不编造。

## 8. 模型抽象层

所有 AI 能力抽象为统一接口，全部走 **OpenAI 兼容协议**，均可配置：

- **对话/理解模型**：分两档——
  - `小模型`：干活，可并行多 agent（快、便宜）。
  - `大模型`：审核、复杂重组、整合回答。
  - 各自可配独立的 base_url、api_key、模型名。
- **Embedding 模型**：向量索引用，可配。
- **工具能力（可插拔）**：
  - `联网搜索`：需要时补充最新信息。
  - `生成图片`：需要时生成示意图并存入附件。
- 全可插拔：以后换本地模型 / 换供应商，只改配置，不动业务代码。

## 9. MVP 范围与分期

### 第一期（MVP）

- **Web 聊天界面（React）**：发文字、传文件、看带来源的回答、下载返回的附件、浏览知识库目录视图。
- **后端大脑（FastAPI）**：
  - 写入流水线（理解 → 找关联 → 决策放置 → 写 md → git commit → changelog）。
  - 重叠拿不准时问用户（C）。
  - 混合检索回答带来源（D）。
  - 附件解析入索引 + 原件下载。
  - 模型抽象层。

### 第二期

- 后台"园丁"定期巡检重组（大改动审批）。
- 大模型审核环节。
- 联网搜索 + 生成图片工具。

### 第三期

- 桌面 Spotlight 入口（全局快捷键）。
- 微信 / 飞书机器人。

## 10. 技术选型

- 后端：**Python + FastAPI**；前端：**React**。
- **文档解析**：微软 `markitdown`，统一把 word/ppt/excel/pdf 转文本入索引（原件仍原样保存）。
- **向量库**：`Chroma` 或 `LanceDB`（本地文件型，零额外服务，可重建）。
- **全文检索**：`SQLite FTS5`（内置、快、无依赖）。
- **git 操作**：`GitPython`。
- **模型调用**：`openai` SDK（兼容任何 OpenAI 协议的服务）。

## 11. 验证与测试

- **核心闭环手测**：录入 5~10 条内容（含故意重复的），检查归置是否合理、重复是否被识别、结构是否清晰。
- **关键逻辑单元测试**：放置决策、去重判断、git 提交、检索命中。
- **小评测集**：一批样例笔记 + 期望归置结果，用于回归。

## 12. 待定 / 后续细化

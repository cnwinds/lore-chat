# ADR 2026-09-29：分区检索底座

## 状态

已采纳（2026-09-29）。阶段 A（底座 + 角色知识卡接入）已落地；阶段 B（文档库、会话迁入）已落地，见 [ADR 2026-09-29 文档库与会话迁入](2026-09-29-kb-conversation-retrieval-migration.md)。

## 背景

现网检索有两套、外加一套私有实现：

- **文档库 / 会话**：FTS5（`trigram`）+ Chroma 向量 + RRF 融合，由 `Retriever` 四条 lane 拼起来（`kb_fts` / `kb_vec` / `conv_fts` / `conv_vec`）。表与集合按内容类型各建一套，没有分区概念，可见性靠查询时的路径前缀排除。
- **角色知识卡按轮检索**：P1 另写了进程内词法打分（`card_retrieval.py`），只有字面重叠，同义改写召不回；`recall_cards` 还是 `LIKE`。

继续往下，主人记忆、角色卡、通道共用角色卡都需要检索。若每种内容各写一套，分词、阈值、降级策略会各自漂移。现有栈里还有几处问题，新租户接入时会放大：

1. **查询编译面向关键词。** `compile_search_query` 按空格切词，给模型写的关键词查询用。拿用户整句中文直接查，严格 / 放宽两级都落空，只剩整句 `LIKE`。
2. **两字中文词。** `trigram` 分词器对 2 个汉字的词建不出匹配，只能落 `LIKE` 兜底。
3. **嵌入模型不固定。** `embed` 走候选链故障切换，查询和入库可能用不同模型，向量不可比；换嵌入模型也不会自动重嵌。
4. **回合关键路径。** 每轮注入在异步 `run` 里同步执行；加进嵌入这类网络请求，会卡住事件循环、拖慢首字。

## 决策

1. **建一个分区检索底座。** 新包 `backend/app/index/partitioned/`，对外是 `SearchIndex`。一个 SQLite 库（`{kb}/.kb/index/partitioned.db`）放清单与全文表，向量在现有 `vec/` 目录下另开集合。租户通过它写入与查询，不再自建检索。
2. **索引是派生投影，不是真相。** 真相留在租户自己的库（卡片是 `memory.db`）。命中只作候选：租户必须回源校验状态与作用域，渲染用回源的当前内容。遗忘、删除立即生效，与索引同步是否滞后无关。
3. **分区是硬过滤，调用方必须显式列出。** 没有「搜全部」。分区名 `<族>:<键>`，例如 `cards:role:<id>`、`cards:persona:<id>`；迁移后有 `kb`、`conv`；以后可有 `memory:<owner>`。谁能看哪个分区由租户在调用前决定（通道人设看不到左栏角色卡与主人记忆），底座只执行。
4. **同族一张表。** 每个族有自己的全文表和向量集合：卡片几十字、文档块近千字，长度归一与词频统计不能混在一起；一个族的过滤出错也漏不到别族。
5. **一套分词，两端共用。** 汉字、假名、谚文按连续串切二字组（单字保留），其余文字按词、小写，先做 NFKC。FTS5 用 `unicode61` 对预分词文本建索引。查询端用同一分词后 OR 检索、`bm25` 排序：整句自然语言和关键词都能查，两字词可命中。分词有版本号，升版本就从清单重建全文表。
6. **嵌入按模型分集合。** 集合名带族与模型指纹；每项记下所用模型。模型变更后后台逐批重嵌，旧集合清空后删除。查询向量的模型与当前模型不一致时，本次不走向量。一次查询只嵌入一次，所有分区共用，另有小容量缓存。
7. **有延迟预算，也能降级。** 查询带向量截止时间：全文同步先跑，向量超时就只用全文，超时不记成模型故障。没配嵌入模型时也只用全文。回合内调用放到线程里，不占事件循环。
8. **写入走对账。** 租户交出某分区的期望全集（`id`、文本、少量元数据），底座按内容哈希比对清单，只增删改有差异的项。全文同步写，向量标记待补，由后台 worker 限流补上，失败退避重试。租户在自身变更点触发对账；启动、每小时维护、重建索引时再全量对账兜底。
9. **底座出信号，租户定门槛。** 底座对每个命中给出 `bm25`、命中词、稀有命中词（按族内文档频率）、余弦分，并做 RRF 融合；采纳门槛按族可配，由租户判断。
10. **迁移顺序。** 角色知识卡先接入，替换 `card_retrieval.rank_cards` 与 `recall` 的 `LIKE`。文档库、会话之后单独迁：保持 `search_kb` / `search_conversations` 的输出契约不变，用检索质量用例验收；迁完前旧索引照旧运行。

## 后果

- 新增 `partitioned.db` 与 `pidx_*` 向量集合；随 `.kb/index/` 一起导出。导入后启动时全量对账补齐。
- 按轮卡片检索多了语义召回：每轮最多多一次查询嵌入，不超过预算。若该作用域的已确认卡全部进了核心块，就跳过检索，不嵌入。
- `reindex_all` 增加各租户全量重建；卡片的向量由后台补。
- 旧栈中的第 1–3 条问题，在文档库 / 会话迁入前仍然存在。迁移时底座还要补元数据过滤（会话的 `conversation_id` / 时间范围 / 说话人）和分页游标。
- `card_retrieval.py` 删除，分词规则收进底座。

## 明确不采用

- 在现有 `fts.db` / `kbs` 集合上加分区列：会把新契约混进旧表，迁移时两边都得改
- 各租户各写一套检索
- 用索引文本直接渲染、把索引当真相
- 默认搜全部分区
- 为中文分词引入 jieba 一类依赖：二字组确定、零依赖，够用；分词有版本号，以后可换
- 回合内同步等待嵌入、不设预算
